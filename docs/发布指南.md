# 构建与发布指南

本文档面向负责 Apex SSH 安装包和 GitHub Release 的维护者。

## 本地构建

```bash
pnpm install

# Windows x64 默认本地构建
pnpm dist

# Windows x64
pnpm run dist:win

# Windows x64 + arm64（GitHub Actions 发布使用）
pnpm run dist:win:all

# Linux / macOS 双架构
pnpm run dist:linux
pnpm run dist:mac
```

产物统一写入 `release/`：

- Windows x64 / arm64：NSIS `.exe`，以及应用内更新所需的 `latest*.yml` 元数据与 `.blockmap` 块映射
- Linux x64 / arm64：Debian `.deb` 和 RPM `.rpm`
- macOS x64 / arm64：`.dmg`

所有平台的公开安装包文件名统一使用 `x64` 和 `arm64` 架构标识。Linux 文件名在架构前增加 `DEB` 或 `RPM` 格式标识，便于 GitHub Release 按格式分组排序；包内部仍使用 DEB/RPM 各自要求的标准架构名称。

macOS 构建会通过系统的 `sips` 和 `iconutil` 从 `resources/icon.png` 生成 `resources/icon.icns`，因此必须在 macOS 上运行。不要在 Windows 上交叉构建 macOS 发布包。

## Electron 下载加速

仓库的 [`.npmrc`](../.npmrc) 已配置 Electron npmmirror 镜像。也可为单次构建设置环境变量：

```powershell
$env:ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
pnpm dist
```

## GitHub Actions 发布

[构建并发布安装包](../.github/workflows/发布.yml) 支持两种触发方式：

- 在 GitHub Actions 页面手动运行：构建三个平台并保留 14 天，适合发布前验证。
- 推送 `v*` 标签：构建三个平台、校验标签与 `package.json` 版本一致，并自动创建 GitHub Release。

正式发布示例：

```bash
# 先更新 package.json 的 version 并提交
git tag -a v0.1.1 -m "发布 v0.1.1"
git push origin main
git push origin v0.1.1
```

标签必须严格等于 `v` 加 `package.json` 版本，例如版本为 `0.1.1` 时使用 `v0.1.1`。

## Windows 应用内更新

Windows 安装版内置基于 electron-updater 的应用内更新：客户端启动后在后台检查本仓库 GitHub Releases 的更高稳定版本，发现后自动下载，用户正常退出应用时静默安装；设置“关于”页也可手动检查更新，或在下载完成后立即重启更新。macOS 与 Linux 暂不支持应用内更新。

- 更新元数据（`latest.yml`、`latest-arm64.yml` 与对应 `.blockmap`）由 NSIS 构建自动生成，发布工作流随安装包一并上传到 GitHub Release，发布时无需额外操作；更新器依赖这些文件定位版本、校验与下载，不得从 Release 中删除。
- 更新源仓库在 `package.json` 的 `build.publish` 中配置（`dunhanson/apex-ssh`）；客户端只读取公开 Release，不携带任何 GitHub Token 或发布凭证。
- 安装包为按用户安装（NSIS `perMachine: false`），静默安装不需要管理员权限。
- 正式启用自动升级通道前必须配置 Windows 代码签名（见下文）；无签名安装包不应作为正式自动升级通道。
- Windows 开发环境（未打包）可在“关于”页手动检查更新（更新源取项目根目录 `dev-app-update.yml`，须与 `build.publish` 保持一致），用于验证更新通道连通；开发环境不做启动后台检查，也不会下载或安装。非 Windows 环境不支持应用内更新。

发布新版本验证应用内升级时，用上一正式版本的安装包覆盖安装旧版，启动后等待后台检查与下载，再分别验证退出时静默安装和“立即重启更新”。

## Windows 签名

未配置证书时 CI 会生成无签名安装包。正式签名前，在仓库 `Settings > Secrets and variables > Actions` 配置：

- `WINDOWS_CSC_LINK`：代码签名证书的 HTTPS 地址或 Base64 编码内容
- `WINDOWS_CSC_KEY_PASSWORD`：证书密码

## macOS 签名与公证

未配置证书时 CI 会生成无签名安装包。正式发布需要 Apple Developer ID Application 证书，并配置：

- `MACOS_CSC_LINK`：`.p12` 证书的 HTTPS 地址或 Base64 编码内容
- `MACOS_CSC_KEY_PASSWORD`：证书密码
- `APPLE_ID`：Apple 开发者账号
- `APPLE_APP_SPECIFIC_PASSWORD`：Apple ID 专用密码
- `APPLE_TEAM_ID`：Apple Developer Team ID

electron-builder 检测到完整变量后会自动签名并提交 Apple 公证。任何密钥都不得写入仓库。

## 发布前验证

CI 构建成功只证明安装包可以生成。每次正式发布仍需在真实 Windows、Linux 和 macOS 设备上验证：

- 安装、首次启动、卸载或拖入 Applications
- 密码与密钥凭证的保存、读取和删除
- SSH 密码认证、密钥认证、终端交互和断线恢复
- SFTP 上传、下载、暂停、恢复和冲突处理
- 最小化、最大化、关闭和多窗口行为

Linux 的密码加密依赖桌面密钥环，应至少覆盖 GNOME Keyring 或 KWallet。macOS 和 Linux 当前沿用自绘无边框窗口，发布前必须检查窗口控制与系统习惯是否可接受。
